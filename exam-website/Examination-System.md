# คู่มือระบบข้อสอบ (Examination System)

เอกสารนี้สรุปการทำงานของระบบข้อสอบตั้งแต่การเตรียมข้อมูลโดยผู้ดูแล การแสดงจำนวนข้อสอบ การเริ่มสอบ การสุ่มข้อสอบและตัวเลือก การจับเวลา การตรวจคะแนน ไปจนถึงการบันทึกผลและคลังข้อผิดพลาด

> ขอบเขตของเอกสารนี้อ้างอิงจากโค้ดใน `exam-website/src` ณ วันที่จัดทำ หากมีการแก้ schema ของ Supabase หรือเพิ่ม API ควรปรับเอกสารนี้ให้ตรงกับการทำงานจริงเสมอ

---

## 1. ภาพรวมการทำงาน

ระบบมีองค์ประกอบหลักดังนี้:

1. **Categories** - หมวดหมู่หรือวิชา
2. **Questions** - คลังข้อสอบของแต่ละหมวด
3. **Exam Session** - การสอบหนึ่งครั้งของผู้ใช้
4. **Mistake Bank** - รายละเอียดคำตอบผิดและคำอธิบายสำหรับการทบทวน
5. **User Question History** - ประวัติข้อสอบรายผู้ใช้ที่ซิงค์ผ่าน Supabase

ลำดับการทำงานโดยรวม:

```text
ผู้ดูแลสร้างหมวดและข้อสอบ
        ↓
ผู้ใช้เปิดหน้า Home
        ↓
ระบบนับข้อสอบ active แยกตามหมวด
        ↓
ผู้ใช้เลือกหมวดและเปิดหน้า Exam Setup
        ↓
ระบบโหลดข้อสอบ active ของหมวดนั้น
        ↓
ผู้ใช้เลือกจำนวนข้อและเวลา
        ↓
ระบบเลือกข้อสอบตามประวัติ แล้วสุ่มลำดับ
        ↓
ระบบสลับตัวเลือกตามการตั้งค่าของข้อสอบ
        ↓
ผู้ใช้ทำข้อสอบและส่งคำตอบ
        ↓
ตรวจคะแนนและบันทึกประวัติ
```

ไฟล์หลัก:

| หน้าที่ | ไฟล์ |
|---|---|
| หน้าเลือกหมวดและนับจำนวนข้อ | `src/pages/user/Home.jsx` |
| ตั้งค่าและทำข้อสอบ | `src/pages/user/ExamSession.jsx` |
| คลังข้อผิด | `src/pages/user/MistakeBank.jsx` |
| สร้าง/แก้ไขข้อสอบ | `src/components/admin/QuestionForm.jsx` |
| นำเข้าข้อสอบจำนวนมาก | `src/components/admin/BulkImportModal.jsx` |
| Supabase client | `src/lib/supabase.js` |

## 2. ข้อมูลข้อสอบ

ข้อสอบอยู่ในตาราง `questions` และมีข้อมูลสำคัญที่ระบบใช้ดังนี้:

| ฟิลด์ | ความหมาย |
|---|---|
| `id` | รหัสข้อสอบ |
| `category_id` | หมวดหมู่ของข้อสอบ |
| `question_text` | เนื้อหาโจทย์ |
| `options` | Array ของตัวเลือกคำตอบ |
| `correct_option` | Index ของตัวเลือกที่ถูกต้อง โดยเริ่มจาก `0` |
| `is_options_randomized` | อนุญาตให้สลับตัวเลือกหรือไม่ |
| `is_active` | เปิดให้ผู้ใช้เห็นและนำไปสอบหรือไม่ |
| `explanation` | คำอธิบายเฉลย |
| `image_url` | รูปโจทย์ ถ้ามี |
| `explanation_image_url` | รูปคำอธิบาย ถ้ามี |

### รูปแบบ Index ของตัวเลือก

ตัวเลือกใช้ zero-based index:

```text
options[0] = ตัวเลือก A
options[1] = ตัวเลือก B
options[2] = ตัวเลือก C
options[3] = ตัวเลือก D
```

ระบบรองรับตัวเลือกตั้งแต่ 2 ถึง 6 ข้อ ดังนั้น `correct_option` ต้องเป็น index ที่มีอยู่จริงใน `options` เสมอ

## 3. การสร้างและนำเข้าข้อสอบ

### 3.1 สร้างหรือแก้ไขทีละข้อ

ใน `QuestionForm.jsx` ผู้ดูแลสามารถ:

- กรอกโจทย์
- เพิ่มตัวเลือกได้สูงสุด 6 ตัวเลือก
- เลือกเฉลย
- เปิด/ปิดการสลับตัวเลือก
- เปิด/ปิดการใช้งานข้อสอบ
- แนบรูปโจทย์และรูปคำอธิบาย

เมื่อบันทึก ระบบเก็บ `correct_option` เป็น index ของตัวเลือกก่อนการสุ่ม ตัวเลือกจะไม่ถูกสลับในฐานข้อมูล

### 3.2 นำเข้าหลายข้อ

ใน `BulkImportModal.jsx` ระบบอ่านรูปแบบ:

```text
1. โจทย์
A. ตัวเลือกที่ 1
B. ตัวเลือกที่ 2
C. ตัวเลือกที่ 3
D. ตัวเลือกที่ 4
ANS: B
EXP: คำอธิบาย
---
```

ตัวอักษร `A`, `B`, `C`, `D` จะถูกแปลงเป็น index `0`, `1`, `2`, `3` ตามลำดับ และข้อสอบที่นำเข้าจะตั้งค่า `is_options_randomized = true`

> ควรตรวจสอบเฉลยในหน้าพรีวิวก่อนบันทึก เพราะระบบจะยึดตำแหน่งตัวเลือกตามข้อมูลที่นำเข้า

## 4. หน้า Home และการนับจำนวนข้อสอบ

`Home.jsx` โหลด:

1. หมวดที่ `categories.is_active = true`
2. ข้อสอบที่ `questions.is_active = true`

จากนั้นนับจำนวนข้อสอบด้วย `category_id`:

```text
จำนวนของหมวด = จำนวน questions ที่มี category_id ตรงกันและ is_active = true
```

ค่าใน Card หน้า Home จึงเป็นจำนวนข้อสอบที่พร้อมใช้จริง ไม่ใช่จำนวนข้อสอบทั้งหมดที่รวมข้อสอบฉบับร่างหรือข้อสอบที่ปิดใช้งาน

เมื่อกดเริ่มสอบ ระบบส่งผู้ใช้ไปที่:

```text
/exam/<categoryId>
```

## 5. การโหลดข้อสอบในหน้า Exam Setup

`ExamSession.jsx` อ่าน `categoryId` จาก URL และโหลดด้วยเงื่อนไขเดียวกับหน้า Home:

```js
supabase
  .from('questions')
  .select('*')
  .eq('category_id', normalizedCategoryId)
  .eq('is_active', true)
```

ก่อน query ระบบตรวจว่า `categoryId`:

- มีค่า
- ไม่ใช่ `undefined`
- ไม่ใช่ `null`
- ไม่มี whitespace ที่ไม่จำเป็น

หาก ID ไม่ถูกต้องหรือไม่พบข้อสอบ ระบบจะแจ้งเตือนและกลับไปหน้า Home แทนการปล่อยให้ query ทำงานโดยไม่มีตัวกรอง

ดังนั้นจำนวนข้อสอบบน Home และจำนวนสูงสุดใน Exam Setup ควรตรงกัน เพราะใช้แหล่งข้อมูลและเงื่อนไขเดียวกัน

## 6. การตั้งค่าก่อนเริ่มสอบ

ผู้ใช้เลือกได้:

### จำนวนข้อ

- ค่าเริ่มต้น: 10 ข้อ หรือจำนวนข้อทั้งหมดถ้ามีน้อยกว่า 10
- เลือกตัวเลือกสำเร็จรูป เช่น 10, 20, 30 และทั้งหมด
- กรอกจำนวนเองได้
- ระบบไม่ให้เกินจำนวนข้อสอบ active ในหมวดนั้น

### เวลา

- ไม่จับเวลา
- 30 นาที
- 60 นาที
- กำหนดเอง 1-120 นาที

เมื่อกดเริ่มสอบ ระบบจะคำนวณค่าที่ปลอดภัยอีกครั้ง หากค่าที่กรอกไม่ถูกต้องจะใช้ค่าเริ่มต้นแทน

## 7. แหล่งข้อมูลประวัติผู้ใช้

### 7.1 ประวัติข้อสอบที่เคยทำ

เก็บในตาราง `user_question_history` โดยใช้คีย์ร่วม:

```text
user_id + question_id
```

ฟิลด์สำคัญ:

| ฟิลด์ | ความหมาย |
|---|---|
| `seen_count` | จำนวนครั้งที่ข้อสอบถูกส่งในชุดสอบ |
| `last_seen_at` | เวลาที่ทำข้อสอบล่าสุด |
| `last_result` | `correct`, `wrong` หรือ `unanswered` |

เมื่อส่งข้อสอบ ระบบจะอ่าน `seen_count` เดิมแล้วเพิ่มขึ้น 1 ก่อน upsert กลับไปยัง Supabase ประวัติจึงซิงค์ได้ทุกอุปกรณ์

### 7.2 ประวัติข้อผิดและรายละเอียดการทบทวน

ระบบใช้ `user_question_history.last_result = 'wrong'` เป็นตัวบอกว่าผลล่าสุดของข้อนั้นผิด และใช้ `mistake_bank` สำหรับรายละเอียดคำตอบผิด/คำอธิบาย โดยกรอง:

```text
user_id = ผู้ใช้ปัจจุบัน
is_resolved = false
```

เมื่อผู้ใช้กด “เข้าใจแล้ว” ระบบจะอัปเดตทั้ง `mistake_bank.is_resolved` และ `user_question_history.last_result = 'correct'` เพื่อไม่ให้ข้อดังกล่าวกลับเข้าสู่คลังข้อผิดหรือโควต้าสุ่มข้อผิดอีก

## 8. ลอจิกการสุ่มข้อสอบ

เมื่อเริ่มสอบ ระบบแบ่งข้อสอบ active ของหมวดนั้นเป็น 3 กลุ่ม:

1. **Mistake pool** - เคยตอบผิดและยังไม่ resolved
2. **Unseen pool** - ไม่มีประวัติ หรือมี `seen_count = 0`
3. **Seen-correct pool** - เคยเห็นแล้วและไม่อยู่ในรายการข้อผิด

### โควต้าการเลือก

| ลำดับ | กลุ่ม | วิธีเลือก |
|---|---|---|
| 1 | ข้อผิด | ประมาณ 20% ของจำนวนข้อสอบที่เลือก |
| 2 | ยังไม่เคยเห็น | เติมต่อให้ครบจำนวนที่เลือก |
| 3 | เคยทำถูก | ใช้เติมเมื่อสองกลุ่มแรกมีไม่พอ |

ตัวอย่างการสอบ 10 ข้อ:

```text
ข้อผิดประมาณ 2 ข้อ
ข้อที่ยังไม่เคยเห็นประมาณ 8 ข้อ
ถ้าข้อที่ยังไม่เคยเห็นไม่พอ จะเติมด้วยข้อที่เคยทำถูก
```

> สัดส่วน 20% เป็นเป้าหมาย ไม่ใช่การรับประกัน หากมีข้อผิดน้อยกว่าที่ต้องการ ระบบจะใช้ข้อสอบจากกลุ่มถัดไป

ข้อสอบที่ถูกเลือกจากแต่ละกลุ่มจะถูกสุ่มก่อน แล้วสุ่มรวมอีกครั้งเพื่อไม่ให้ข้อผิดอยู่ต้นชุดเสมอ

## 9. วิธีสุ่มลำดับ

ระบบใช้ Fisher-Yates Shuffle ใน `ExamSession.jsx`:

```js
for (let i = array.length - 1; i > 0; i--) {
  const j = Math.floor(Math.random() * (i + 1))
  swap(array[i], array[j])
}
```

ฟังก์ชันสร้าง Array ใหม่ก่อนสุ่ม จึงไม่แก้ Array ต้นฉบับโดยตรง และไม่ใช้รูปแบบที่มี bias เช่น:

```js
array.sort(() => Math.random() - 0.5)
```

การสุ่มนี้เป็นการสุ่มฝั่ง Browser หลังโหลดข้อสอบทั้งหมดแล้ว ไม่ใช่การใช้ `ORDER BY random()` ในฐานข้อมูล

## 10. การสลับตัวเลือกและการตรวจเฉลย

ถ้า `is_options_randomized = true`:

1. สร้างคู่ข้อมูลระหว่างข้อความตัวเลือกกับ index เดิม
2. สุ่มคู่ข้อมูลด้วย Fisher-Yates
3. คำนวณตำแหน่งเฉลยใหม่จาก index เดิม
4. เก็บ index เดิมของตัวเลือกที่แสดงไว้ใน `originalOptionIndices`

ตัวอย่าง:

```text
ก่อนสุ่ม:
  options = [A, B, C, D]
  correct_option = 2

หลังสุ่ม:
  displayOptions = [D, B, A, C]
  displayCorrectOption = 3
  originalOptionIndices = [3, 1, 0, 2]
```

ถ้าผู้ใช้เลือกตำแหน่งที่ 3 ระบบจะตรวจจาก `displayCorrectOption` และรู้ว่าตัวเลือกนั้นคือ index เดิม `2`

ถ้าปิดการสลับตัวเลือก:

- แสดงตัวเลือกตามลำดับเดิม
- ใช้ `correct_option` เป็นตำแหน่งเฉลย
- สร้าง `originalOptionIndices` ตามจำนวนตัวเลือกจริง จึงรองรับ 2-6 ตัวเลือก

## 11. การทำข้อสอบและจับเวลา

คำตอบของผู้ใช้เก็บใน state รูปแบบ:

```text
userAnswers[questionId] = displayOptionIndex
```

ระบบจะไม่เปลี่ยนคำตอบหลังเข้าสู่สถานะ `submitted`

เมื่อเปิดจับเวลา:

- ตัวจับเวลาลดลงทุก 1 วินาที
- เมื่อเหลือ 0 ระบบส่งข้อสอบอัตโนมัติ
- ข้อที่ยังไม่ตอบจะถูกตรวจเป็นข้อผิด/ไม่ได้ตอบ

หากผู้ใช้พยายามออกระหว่างทำข้อสอบและมีคำตอบแล้ว ระบบจะแสดงคำเตือนก่อนออก

---

## 12. การส่งข้อสอบและตรวจคะแนน

เมื่อส่งข้อสอบ ระบบวนตรวจทุกข้อ:

```text
คำตอบที่เลือก === displayCorrectOption
```

ผลลัพธ์:

- ตอบถูก: เพิ่มคะแนน 1 คะแนน
- ตอบผิด: เพิ่มรายการลงคลังข้อผิด
- ไม่ตอบ: ถือเป็นข้อผิดและบันทึก `user_answer = null`
- ทุกข้อที่อยู่ในชุดสอบจะ upsert เข้า `user_question_history`

เมื่อทำข้อที่เคยผิดแล้วตอบถูก:

- อัปเดต record ที่ตรงกันใน `mistake_bank` ให้ `is_resolved = true`
- อัปเดต `user_question_history.last_result = 'correct'`

## 13. การบันทึกลง Supabase

### `exam_sessions`

บันทึก:

- `category_id`
- `total_questions`
- `score`
- `completed_at`

### `mistake_bank`

บันทึกข้อที่ตอบผิดหรือไม่ได้ตอบ โดยมีข้อมูลหลัก:

- `question_id`
- `user_answer`
- `is_resolved`
- `session_id`
- `user_id` ตามค่าเริ่มต้น/กฎของฐานข้อมูล

หากผู้ใช้กด “เข้าใจแล้ว” จากหน้า Mistake Bank ระบบจะ:

1. อัปเดตข้อผิดของผู้ใช้และข้อเดียวกันที่ยัง `is_resolved = false`
2. เอาข้อนั้นออกจากรายการบนหน้าจอ
3. อัปเดต `user_question_history.last_result` เป็น `correct`

ดังนั้นข้อดังกล่าวจะไม่ถูกนำกลับมาเป็นข้อผิดในการสุ่มครั้งถัดไป

## 14. กรณีข้อมูลไม่สอดคล้องและแนวทางตรวจสอบ

### จำนวนข้อ Home ไม่ตรงกับ Exam Setup

ตรวจตามลำดับ:

1. URL ต้องเป็น `/exam/<categoryId>`
2. `categoryId` ต้องตรงกับ `categories.id`
3. ข้อสอบต้องมี `is_active = true`
4. ต้องตรวจว่า Home และ Exam Setup ใช้ฐานข้อมูล/Project Supabase เดียวกัน
5. หากเพิ่ง deploy ให้ตรวจว่า hosting ใช้ build ล่าสุด

### ข้อผิดยังกลับมา

ตรวจ:

1. ผู้ใช้เข้าสู่ระบบบัญชีเดียวกันหรือไม่
2. `mistake_bank.user_id` และ `user_question_history.user_id` ตรงกับผู้ใช้ปัจจุบันหรือไม่
3. `user_question_history.last_result` เป็น `wrong` อยู่หรือไม่
4. `mistake_bank.is_resolved` เป็น `false` อยู่หรือไม่
5. RLS ของทั้งสองตารางอนุญาตให้ผู้ใช้อ่านและอัปเดตข้อมูลของตนเองหรือไม่

### ตรวจเฉลยผิดหลังสลับตัวเลือก

ตรวจ:

1. `correct_option` เป็น zero-based index
2. จำนวนสมาชิกของ `options` ถูกต้อง
3. ค่า `correct_option` ไม่เกิน `options.length - 1`
4. ข้อมูลที่นำเข้าผ่าน Bulk Import มี `ANS` ตรงกับตัวเลือกจริง

---

## 15. ข้อจำกัดปัจจุบัน

1. การเพิ่ม `seen_count` เป็น read-then-upsert ที่ฝั่ง Client หากมีการส่งสอบพร้อมกันหลายแท็บอาจเกิด race condition ควรย้ายไป RPC/ฟังก์ชันฐานข้อมูลเมื่อระบบต้องการความแม่นยำระดับ transaction
2. การสอบโหลดข้อสอบ active ทั้งหมวดเข้ามาที่ Browser ก่อนสุ่ม หากคลังใหญ่มากอาจต้องปรับเป็น server-side selection หรือ pagination
3. สัดส่วนข้อผิด 20% เป็นค่าเป้าหมาย อาจไม่ครบเมื่อมีข้อผิดไม่พอ
4. การบันทึกข้อมูลสอบและประวัติเกิดหลังส่งผลสอบแล้ว หาก Supabase ล้มเหลว ผู้ใช้ยังเห็นผลสอบ แต่ประวัติอาจบันทึกไม่ครบ
5. การสุ่มด้วย `Math.random()` เหมาะกับการกระจายข้อสอบทั่วไป แต่ไม่ใช่การสุ่มที่ใช้สำหรับงานความปลอดภัยหรือการจับสลากที่ต้องตรวจสอบได้

---

## 16. แนวทางพัฒนาต่อ

ตาราง `user_question_history` รองรับการซิงค์ประวัติข้ามอุปกรณ์แล้ว:

| ฟิลด์ | ความหมาย |
|---|---|
| `user_id` | ผู้ใช้ |
| `question_id` | ข้อสอบ |
| `seen_count` | จำนวนครั้งที่เห็น |
| `last_seen_at` | เวลาที่เห็นล่าสุด |
| `last_result` | ผลล่าสุด เช่น `correct`, `wrong`, `unanswered` |

โครงสร้างนี้ช่วย:

- เก็บ `seen` บนฐานข้อมูลแทน LocalStorage
- คำนวณข้อที่ยังไม่เคยเห็นจากข้อมูลจริงของผู้ใช้
- ซิงค์ประวัติทุกอุปกรณ์
- ทำ analytics รายข้อได้ละเอียดขึ้น
- รองรับการสุ่มจากฐานข้อมูลเมื่อจำนวนข้อสอบเพิ่มขึ้นมาก

ก่อนนำไปใช้จริงควรเพิ่ม RLS ให้ผู้ใช้เข้าถึงเฉพาะข้อมูลของตนเอง และพิจารณาใช้ RPC/transaction เพื่อบันทึกผลสอบกับข้อผิดให้เป็นชุดเดียวกัน

## สรุปสั้น

ระบบปัจจุบันทำงานตามลำดับ:

```text
โหลดข้อสอบ active ตาม category
  → เลือกข้อผิดประมาณ 20%
  → เติมข้อที่ยังไม่เคยเห็น
  → เติมข้อที่เคยทำถูกถ้ายังไม่ครบ
  → สุ่มลำดับข้อสอบด้วย Fisher-Yates
  → สลับตัวเลือกตามการตั้งค่า
  → ตรวจคำตอบจากตำแหน่งที่แสดง
  → บันทึกคะแนนและข้อผิด
  → อัปเดตประวัติสำหรับรอบถัดไป
```

แกนสำคัญที่ต้องรักษาให้สอดคล้องกันคือ `category_id`, `is_active`, zero-based option index, `user_question_history.user_id`, `user_question_history.last_result` และ `mistake_bank.is_resolved`
